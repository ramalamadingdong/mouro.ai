Designing a circuit board end to end with an AI agent

Parts, netlist, placement, routing, gerbers. I review, it does the work.

August 16, 2026, updated November 15, 2026. 24 min read.

TopicsKiCad, AI Agents, Hardware, Claude Code, PCB

The short version

  • The design lives in a CSV, one row per pin, every row citing the document it came from. Scripts build the schematic and the board from it. Nothing in KiCad is edited by hand.
  • One board.toml per board drives the build passes and the checker off the same numbers, in one coordinate frame.
  • The build is a chain of idempotent passes. Routing is a separate script off a snapshot, so placement can be re-run without paying for a re-route.
  • Freerouting, single threaded and constrained: plane layers marked unroutable, anything critical pre-routed as fixed copper.
  • Five levels of checking. The last one parses the exported gerbers, because those are the files the factory builds from.
  • Fixes go in the pipeline, never in the board file. The next rebuild wipes anything done by hand.
  1. netlist.csv source of truth
  2. schematic round trip diff
  3. board place, zones, fanout, silk ERC
  4. routed Freerouting, -mt 1 DRC ×5
  5. gerbers what the factory builds validate_gerbers

All of it is public, and the board this post walks through is in the repo. You can clone it, build it, and get the same gates. That particular board hasn't been fabricated; others designed this way have.

This is the setup I use to have an AI agent design a whole PCB: it picks the parts, writes the netlist, places and routes the board, and exports gerbers a fab will build. My job is review.

The pipeline is public, and so is the board I use as the example throughout. Clone the repo, run four commands, and you should get the same output I did.

Where this stands

The pipeline is pcb-agent, GPL-3.0. The fab-output checker stands alone, no dependencies, as gerber-check, MIT. The example board is in the repo with its full design record.

This particular board has not been fabricated. It passed its pre-order gates, which means the design files are consistent with each other and with the rules I wrote. It does not mean the board works.

Boards designed this way have been built, but I'm not ready to publish those. The example is the one you can clone, build and check yourself.

Update, September 30, 2026. A month after sign-off, three new gates found three defects the earlier ones had passed. The Qwiic connector was rotated 180°, so its socket opened into the board. Sixteen pads on eight rotated passives lay along the part axis instead of across it. And the completion pass had laid about 200 redundant segments and 69 vias on nets that were already routed, because its connectivity model never joined a segment's two ends. All three are fixed and now gated, and the example was rebuilt from netlist.csv. The sign-off numbers further down are the August ones; the repo README has the current set.

The board

A power and I/O demo shield for the Arduino UNO Q. Screw-terminal input at 7–24 V behind reverse-polarity protection, a TPS54331 buck making 5 V for shield loads, an INA226 monitoring the whole stack's current and bus voltage over I²C, four BSS138 level-shift channels between the UNO Q's 3.3 V headers and 5 V peripherals, Qwiic passthrough, an RGB status LED. Four layers, top side only, 24 BOM lines.

The circuit is ordinary on purpose, but the layout is not easy. A switching converter sits a few millimetres from a 0.5 mm pitch part, inside the UNO form factor — which fixes the outline, the four mounting holes and all 32 header pins before you place anything of your own. Every rule in its config exists for a reason you can point at on the board: the buck's exposed pad is its only real heatsink, VIN carries up to 4 A, and the UNO Q's Wi-Fi antenna sits directly under the top-left corner, so copper there detunes the radio.

Those coordinates aren't mine. The outline, the hole pattern, the header positions and the antenna keepout were extracted from Arduino's own documents and fab data for the UNO Q, © Arduino SA, licensed CC BY-SA 4.0. Taking the hole pattern from the manufacturer's drill file instead of a drawing is typical of the method: use the data the factory used.

Where a number below came off a different board, I say so. The method came out of an earlier project, a small data logger — MCU module with Bluetooth, two sensors, a GNSS receiver, storage, USB-C charging, about 60 parts — and several of the lessons here come from mistakes found on its fabricated boards.

The design lives in a CSV, not in KiCad

The schematic isn't the source of truth. A CSV is. The KiCad project is a build output.

One row per pin, every pin of every IC, NC written out where a pin is meant to be unconnected, and a note column that carries the citation. Real rows from this board: 

Net,RefDes,Pin,PinName,Note
VIN_RAW,J1,2,VIN,7-24 V in, matches UNO Q DC_IN range (ABX00162 datasheet 3.2 p.11)
VIN_PROT,Q5,1,S,protected rail out (AO4407A.pdf p.1: pins 1-3 S)
GND,U2,2,A0,address 0x40 = A1:GND A0:GND (INA226 Table 6-2)
BOOT,U1,1,BOOT,bootstrap; 100nF to PH (ds front-page application circuit)

One script turns that into a schematic. Another turns the schematic into a board. Nothing in the KiCad files gets touched by hand. To change the circuit you edit a row and rebuild.

KiCad files are s-expressions full of coordinates. An agent editing them directly is changing geometry it cannot see, and a small error in that format is still a valid file: a label a fraction of a millimetre off its pin parses, renders and passes ERC. The first sign of trouble is a board that doesn't work.

Catching silent breakage you don't the build fails

The round trip check

The schematic generator reads back the file it just wrote, pulls the netlist out of it, diffs that against the CSV, and fails the build if anything doesn't match.

If I could keep only one check, it would be this one. An LLM writing KiCad files will eventually put a label a fraction of a millimetre off a pin. The schematic looks correct, but the net doesn't exist. ERC treats the label as intentionally floating, and DRC never looks at the schematic. Without the round trip you find out when the board comes back and the part doesn't answer on the bus.

Requirements come out of documents

An LLM does not remember a pin map. It reconstructs one, and the reconstruction is often wrong.

Before any wiring, the agent writes down what the hardware has to provide, and every line carries a citation to something it read in that session: a document, a page, a table. Anything recalled from training doesn't count.

This board had no firmware yet, so every requirement came out of Arduino's own material: the datasheet with page numbers as printed, the full pinout, the schematics by sheet number, and the fab data inside their CAD files — the Allegro gerbers and NC drill they actually manufacture from. Sixteen requirements, each with a source. A few that shaped the design:

  • All shield-facing logic is 3.3 V. A0 and A1 aren't 5 V tolerant in any mode, and one digital pin is 3.6 V max even in digital mode — which is why the board needs level shifters at all
  • The shield I²C bus already has 2.2 kΩ pull-ups on the UNO Q itself, found on schematic sheet 20, so the shield adds none. A second set in parallel lowers the pull-up resistance and raises the current every device has to sink, which gives a marginal bus that is hard to diagnose
  • The Wi-Fi antenna occupies a specific rectangle in the top-left corner, extracted from the copper in Arduino's own gerber and confirmed against a 600 DPI render. That rectangle becomes the keepout, on all copper layers, pads included
  • The four mounting holes are Ø3.2 mm NPTH at coordinates taken from the manufacturer's drill file, not from a drawing. The UNO pattern fixes them

When firmware does exist, it's the best requirements source you have, and the agent should read it first. On the data logger that's where bus addresses, sample rates and partition sizes came from, each cited to a file and a line number. That board also had a headless code path already, so a variant with no display and no I/O expander needed no new code at all, just a pin map. The cheapest board variant is one the firmware already supports.

The agent then reads every datasheet against the connection table. This step finds the most, because a BOM with the right ICs on it is usually still missing the parts around them. On the data logger that meant a charger with no load-share path, which reads system load as charge current and trickles the cell forever; no battery sense divider on a board whose firmware reports a battery percentage over Bluetooth; a GNSS receiver with no antenna connector and no RF front end; and IMU pins floating, which sits the part in the wrong interface mode so it never answers.

Have it do the capacity math

Same session, before layout. On this board that's a worst-case VIN current of 3.6 A at the low end of the input range, designed to 4 A, which IPC-2221 turns into a 2.0 mm conductor at 1 oz external copper for a 10 °C rise. The shunt is 10 mΩ, so 4 A puts 40 mV across it — 49% of the INA226's ±81.92 mV range, which leaves headroom above and resolution below. Inductor ripple works out at 0.69 A peak to peak worst case, so peak current is 1.9 A against a 3.2 A saturation rating.

The calculation earns its place in the cases where the answer is bad. On the data logger the logging rate was 21 MB/hour into an 896 kB filesystem, which is two and a half minutes of recording. That's why that board has a microSD socket.

Make it show the arithmetic, and make it write down what it rejected. This board's plan names six parts it didn't use and why: a buck in a package with no exposed pad, which would have deleted the thermal-via lesson the board exists to teach; a current monitor whose 26 V absolute maximum is too close to a 24 V nominal input, because an unloaded 24 V supply drifts above it; a one-chip level shifter whose edge-rate accelerators misbehave on exactly the breadboard wiring a first-time user will do. When a part goes out of stock or a requirement changes, the recorded rejections say which alternatives are already ruled out, and why.

What I use

Harness

Claude Code. Four things matter:

  • Shell and file access across the whole repo, firmware included.
  • Subagents, so part research and layout and firmware work run at the same time.
  • Persistent memory. A board takes weeks, and what the agent learns in one session has to be there when it plans the next revision.
  • A plan doc per revision in the repo: what's in scope, what defect it fixes, how, and a list of checks that have to pass before you order. The check list matters most, because it defines when the revision is done.

Skills

Eleven of them, all from kicad-happy by Andrew Klofas. MIT licensed, and it works with Claude Code and Codex. If you install one thing from this post, install this.

Two things these are good for.

Part selection with the whole picture in it. Every line on this board was checked against JLCPCB's own component endpoint on the day it was signed off: price, stock, and whether the part is Basic or Extended, which is a real cost because each Extended line carries a loading fee. On the data logger the same habit found the expensive version of that problem — a $16.31 part with a seven week lead, whose obvious replacement had more stock but a 22 week lead. The agent found a third option at $2.93, in stock, and gave the reason it worked: the firmware only used three things from the original part, and the replacement puts all three out of its own fusion block. That swap deleted 11 parts, a crystal, half the fanout pads and one layout constraint.

Land patterns out of the drawing, not the text. On this board the RGB LED's common anode is pin 2, which you only learn from the land drawing on page 8. On the data logger a chip antenna's datasheet text said two terminals while the land drawing in the same PDF showed three pads, because the feed terminal sits on a split pad pair. A two pad footprint ships a dead antenna on a board that's otherwise fine.

When a datasheet's text and its drawing disagree, follow the drawing, because the footprint is built from the land pattern.

CAD and the toolchain

kicad-tools by RJ Walters. MIT licensed Python toolkit built for agents. Every command outputs JSON and none of it needs KiCad running. It ships an MCP server and a kct CLI, so the agent calls it as tools and the build scripts call the same things. I use it for checkpoint and restore, board inspection, schematic to PCB, the placement tools, zones, and export. I route with Freerouting instead of the built-in routers.

All the headless stages run in one container now, so none of it has to be installed by hand: KiCad 10 on a digest-pinned base image, Freerouting 1.9.0 fetched by checksum, a pinned kct, and uv holding the Python environment still. 

git clone https://github.com/ramalamadingdong/pcb-agent && cd pcb-agent
python3 scripts/doctor.py       # names every missing piece and the fix
make setup                      # builds the image, fetches the pinned jar
make build route export check  # this board, end to end

Install KiCad natively as well if you want to look at a board — the container has no GUI, and the one X11 thing inside it is a virtual framebuffer that exists solely because Freerouting asks for a screen size it never uses. Match the major version to the boards you build. A KiCad 9 pcbnew loading a KiCad 10 board returns None, with no error and no message.

The build

  add_fiducials        not netlist objects, nothing else will emit them
  add_keepouts         antenna clearance, analog islands, any layer declared a plane
  silk_finish          reposition every refdes on board, draw the markings
  fill, snapshot
                       ---- separate script ----
                       export DSN, freerouting, import SES
                       completion passes, fill, DRC x5
                       export_fab, validate_gerbers

Four things about the shape of this.

One config file per board. board.toml drives the build passes and the gerber checker off the same numbers, in one coordinate frame with the origin at the board's bottom left corner. The same rectangle feeds the keepout rule area, the silkscreen dodge, the router's fence, and the check that the keepout is actually clear in the exported gerbers. Anything you catch by hand becomes a line in it, which is the only reason the checker gets better over time instead of staying wherever it started.

Build and route are separate scripts, and routing starts from a snapshot. Routing is the only slow, non repeatable step, and importing the router's output rewrites the board into a format the rest of the tools can't read. With a snapshot you can iterate on placement 20 times without paying for a re-route.

Every pass is idempotent. Strip and rebuild, don't append. The agent will re-run a stage when it isn't sure whether it already ran. An appending pass turns that into junk copper — on the data logger, nine stray vias inside a module's exposed pad.

The order matters. Mounting holes before the placement loop, so their courtyards are obstacles. Fiducials before the pour refill, so the pour honours their clearance ring. Keepouts before silk, so the silk dodges the rectangles. With the order wrong, every pass still succeeds and the board is wrong.

The passes that exist because of specific tool behaviour

These four are the ones I'd tell anyone to write on day one.

repair_pads, after every optimiser call. The placement optimiser writes absolute board coordinates into each footprint's local pad positions. Both pads of a two pad passive end up at the same point: 

after create-pcb    C17 pads: [('1','-0.775','0'), ('2','0.775','0')]     correct
after optimize      C17 pads: [('1','142.598','92.092'),
                               ('2','142.598','92.092')]                  corrupt

On the data logger it hit 71 of 74 footprints, which is a couple hundred shorts and several hundred clearance errors, and the router can't escape any pad because the pads aren't really there. The repair pass puts every pad back where the footprint library says it goes. Restore the rotation as well as the position. Pad angle in the board file is footprint rotation plus pad rotation, and if you only restore coordinates then every pad on a rotated part comes out axis aligned.

A net table assertion in the build. One KiCad operation rewrites the board into a stripped down format that drops the top level net table and keeps only per pad net names. KiCad reads it fine, DRC reads it fine, every fab export reads it fine. The router builds its net list from that table, so it reports "nets to route: 0" and does nothing, with no error. 

grep -cE '^\s*\(net [0-9]+ ' board_file   # must be N, not 0

A fanout that checks all four spacings it creates. Pad to its own via and via to via aren't enough. Also check the stub running past the next pad's via, where real spacing is pitch - track_width/2 - via_size/2. And check other nets' copper, or an escape via lands on a resistor pad and you get a short, a clearance error, a hole clearance error and a mask bridge that all read like an unrelated footprint problem.

That third spacing is not always satisfiable, and this board is where I found out. Dogbone every pad of the INA226's MSOP-10 and each ring via lands exactly one pad pitch from its neighbour's escape stub. Run the numbers at the board minimum via and track: 0.5 − 0.1 − 0.25 = 0.15 mm, which is exactly the clearance, and equality fails. No via size fixes it, because a smaller via is what that number already assumes. A full fanout of a 0.5 mm pitch part can be arithmetically impossible. The answer was to fan out one pad — the ground pad, which has to reach the inner plane and which no other pass can draw. Every other pin is a routed signal or sits in a pour. Alone, it fits.

Note which clearance applies: DRC uses the larger of the two nets' clearances, so a fine pitch escape running past ground copper gets held to the ground net's rule, not its own.

silk_finish. The same coordinate corruption that hits pads also hits reference and value field positions, and a pad-only repair doesn't touch them. Reposition every refdes back on board, then draw the markings you actually need: orientation arrow, polarity, revision, connector and LED labels. The fab clips anything off board, so without this the boards print bare.

Routing, and what it actually costs

Freerouting, single threaded, version pinned, and headless under xvfb-run.

  • -mt 1. Freerouting warns that multithreaded optimisation can introduce clearance violations, and it does. On the data logger -mt 4 gave about 20 DRC errors; -mt 1 on the same input gave zero, and finished faster (61 s vs 210 s) because it stops when it stops improving instead of running all the passes.
  • Foreground. Backgrounded, it opens the file and exits without routing.
  • Pin the version to your Java. Newer releases need a newer JVM.
  • Budget for the layer you gave up. Declaring an inner layer a plane is the right call for reference integrity, but it's a routing layer gone. On the data logger it left about 25% of nets unrouted. Raise the pass count and finish the remainder with a completion pass.

I get better results from constraining Freerouting than from trying other routers. Pre-route anything critical as fixed copper, mark plane layers unroutable when you export the DSN, and let it do the rest. Then judge the run by its JSON output: the segment count must climb, the unfixed list names the nets completion couldn't finish, and the DRC block shows violation kinds across five runs. Stable kinds are real; unstable ones are DRC nondeterminism.

Setup is automated. Finishing a board still takes iteration.

Getting this board from first placement to zero clearance violations took about 19 rounds, each one an edit to board.toml and a rebuild. Placement alone went 26 errors, then 10, then 6, then warnings-only over four iterations. Several of those rounds needed judgment that no checker supplied. Three are worth knowing before you start.

The router cannot cross a pour. A bounded pour exported to the DSN is fixed copper as far as the router is concerned, and it will not cut through it. The VIN pour on this board reached one pad column past the buck and closed off the corridor east of the chip. So the router took the only path left, which shoved the switch node under the chip and past the feedback pad — the worst place on the board for it to go. The same violation came back for about six rounds while I adjusted router settings. The fix was to shrink the pour.

Place passives by net topology, not by schematic tidiness. The feedback divider and the compensation network started north of the buck, which is where they sit on the schematic. Their pins leave the chip south and east. The router's only short path back grazed pads the whole way, and that was the last cluster of clearance errors on the board. Putting them into a row south of the chip, each rotation chosen so the pad carrying a net faces the track coming into it, cleared them. Rotation is part of placement: a part in the right position facing the wrong way routes as badly as one in the wrong position.

Congestion is a floorplan problem. When completion leaves nets unfixed it usually means a corner is too tight. Give the parts room rather than fighting the router for a path that isn't there.

Four smaller traps, in the order I'd want to be warned about them. KiCad 10 writes the netclass name "Power,Default", and the comma splits the token in the Specctra DSN, so the router reads a class that isn't there and those nets route at the default width. A second pcbnew.LoadBoard after editing zones hands back a bare SwigPyObject with no methods on it, so load once and keep the handle. Zone net assignment resets on board.Add(), so set the net after you add it. And kct zones fill refuses to write its output over its input.

Two things to watch for in any router you evaluate. If it reports "violations": [] on a pass that just laid traces through other nets' pads, its self report isn't evidence. If it lists nets correctly and then emits zero copper, count segments before and after every call so you catch a silent no-op.

Checking

Five levels. Each one catches things the one above it passes.

Level 0, the generator checks itself. Round trip diff of the schematic against the CSV. Every node matches or the build fails.

Level 1, ERC. Cheap, doesn't catch much, run it anyway.

Level 2, DRC, sampled. DRC isn't deterministic. Twelve runs on one unmodified file gave me a violation 0 times in nine runs, once in two, twice in one, with totals moving by plus or minus 2. Run it five or more times and compare which violations appear, not the count. Also fill zones with the real filler first, because the refill-zones flag during DRC fills worse and invents thermal relief errors.

Level 3, the agent reviewing the board. Useful, and the one to trust least, because it reasons from what the build was supposed to do rather than what it did.

Level 4, parse the gerbers. The gerbers are the only files the factory sees.

Level 4 is a script. It catches things nothing above it does:

  • Signal routing on a layer you declared a plane. The data logger had 60 track segments across 17 nets on one, including a line running directly under an RF trace, which breaks its reference plane.
  • Missing mounting holes. They're not netlist objects, so nothing in the build emits them unless you write that pass, and nothing checks unless you write this one.
  • Reference designators and free silk text off the board edge.
  • Fiducials sitting inside a keepout, because keepout rules ban pours, tracks and vias, not pads.
  • Power nets at the default trace width, because the generated netclass patterns (VCC*, VDD*, +*V) match none of the usual power net names. Nothing errors, the traces just come out thin.
  • Fiducials the checker can't see at all. An earlier revision shipped them as bare copper dots with no X2 aperture tag, so gerber-level checking was blind to them. Export with X2 attributes on.

So the script reads the exported package and checks:

  • No signal draws on layers declared planes (net tagged X2 scan)
  • Drill file has every mounting hole at the right size and position
  • Every keepout actually clear, on all four layers
  • Power nets at or above minimum width on every layer (aperture per net scan)
  • All silkscreen inside the board outline
  • Three fiducials, not in a line, outside every keepout
  • Enough thermal vias under the exposed pad
  • The board outline lands where the config says it does, so coordinate rules aren't looking at empty space

One PASS or FAIL per line, non-zero exit if anything fails, run after every export. Rules you haven't configured report SKIP instead of PASS, so a missing check can't be mistaken for a passing one.

Anything you find by hand becomes a check in that script, and the script runs on the fab output, never on the KiCad file.

Where this board ended up, at sign-off:

  • 0 unconnected, 0 clearance violations, identical across five consecutive DRC runs
  • Gerber checker 14 passed, 0 failed. ERC clean
  • All 24 JLC BOM lines verified in stock that day
  • 17 residual DRC items in 3 kinds, every one written down and explained: four are the Qwiic connector's pads, on a part that mounts at the board edge by design; one is a header pin inside a mounting hole's courtyard, both positions fixed by Arduino; twelve are courtyard grazes in the deliberately tight power stage, where the bodies clear and the conservative courtyards touch

That ledger is the first thing I'd read when reviewing someone else's board. A residual violation with a written reason has been looked at; one without a reason has not.

Rules

Fixes go in the pipeline, never in the board file. After routing there are always connectivity problems the router can't sort out: isolated ground pads, pour islands, plane fragments that need links across layers. Fix those by hand and the next rebuild wipes all of it. Write them as a pass. (A layer hop needs vias at both ends. A track on one layer that ends under a pad on another layer connects nothing.)

Save the exact files you order. That means the literal package, not a regenerated copy. Auditing an order only means something if you can prove the zip you're reading is identical to what shipped.

Don't trust what a tool says about itself. Verify with an independent check.

Don't wave off a warning from a checker. Dismissing it replaces a measurement with an assumption.

Don't assume generated defaults match your names. Netclass patterns, layer names, part rotation conventions. Nothing errors, the output is just wrong.

Recheck the numbers in your own plan. On the data logger I'd written down 0.5 mm power traces. At 0.5 mm a trace can't get into a 0.3 mm USB-C pad without breaking clearance to its neighbours, and the router left two dozen nets unrouted. The right number was 0.30 mm, about 1.1 A at 1 oz copper per IPC-2221, which is more than 2x margin on a 500 mA charge current. Then write down why it changed. This board carries the same lesson as a config comment: the wide conductor the IPC math implies can't enter a small pad, so the current path is the plane and the bounded pours, and the width rule is a floor for the checker rather than the design width.

Get the document. Pull the datasheet or the vendor library, cite it, and copy it into the project so an upstream update can't quietly change your geometry later.

Stop twice before the netlist. The agent interviews you, then stops. It writes the plan, then stops. Those two stops are where wrong assumptions get caught cheaply. Without them, an idea-to-board prompt produces sixty confident rows of hallucinated pin numbers, and you find out when the boards arrive.

What this gets you

A build that goes from CSV to gerbers repeatably. A written reason behind every real part choice. Sources cited for everything. A gerber checker that runs on every export. Respins in hours instead of days, because the fixes are in code.

Almost every failure in this post is a failure of observation, not of reasoning: corrupted pad coordinates, dropped rotations, a fanout that doesn't check its own spacing, signals on a reference plane, text off the board, fiducials in a keepout, thin power traces. In each case the agent's intent was right, and it had no way to see that the output didn't match. The pipeline works because every check parses a file instead of asking the agent to look at the board.

One gap remains that no pipeline closes. This board passed every gate I know how to write, and it has never been fabricated. Two of its gates can't close until the order is placed: re-verify every part in stock at order time, and commit the ordered files byte for byte. After that it either powers on, or the failure becomes a new check and an entry in the next revision plan.

None of this replaces bring-up. A design that passes five levels of checks is consistent with itself, and only a powered board shows that it works.

Tools

  • pcb-agent, mine. Everything in this post: the build passes, five slash commands, board.toml, the checker, and this board as the worked example. GPL-3.0, because the build passes import pcbnew. Developed and verified on Linux and WSL with Docker; macOS is untested and native Windows isn't a path. Start at docs/end-to-end.md.
  • gerber-check, mine. Level 4 on its own: one file, no dependencies, doesn't need KiCad, runs on a fab package out of any tool. Non-zero exit, so it drops straight into a Makefile or a pre-order gate. MIT.
  • kicad-happy by Andrew Klofas. Eleven KiCad skills for Claude Code and Codex: schematic and PCB analysis, EMC, SPICE, datasheet extraction, sourcing from DigiKey, Mouser, LCSC and element14, BOM management, and fab prep for JLCPCB and PCBWay. MIT. There's also a test harness that runs the analyzers against thousands of open source KiCad projects.
  • kicad-tools by RJ Walters. Python toolkit for agents to parse and edit KiCad files. MCP server plus a kct CLI, JSON output, doesn't need KiCad running. MIT. Board gallery at kicad-tools.org.
  • KiCad and kicad-cli for ERC, DRC and fab export. The bundled pcbnew Python API does everything else. Pin the major version to the boards you build.
  • Freerouting, Specctra DSN/SES autorouter. Pin the version to your Java, run it single threaded, and run it headless under xvfb-run.
  • uv to pin the Python environment.
  • Claude Code, the harness it all runs in.

All of it is free, and both third-party skill packs are MIT. The UNO Q facts this board is built on come from Arduino's own documents, CC BY-SA 4.0, credited in the example's README.
